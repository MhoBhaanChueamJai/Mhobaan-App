# Spec: ระบบบันทึกการรักษาหมอพื้นบ้านเชื่อม HOSxP และระบบส่งต่อ

15 ต.ค. 2569 · ชื่อทำงาน "หมอบ้านเชื่อมใจ"

> ไฟล์นี้เป็นต้นฉบับของหัวข้อ "ระบบหมอบ้านเชื่อมใจ" ในคลังความรู้ — `scripts/build-kb.py` แบ่งตามหัวข้อ `## N.` (1 หัวข้อ = 1 หน้าในคลัง)

## 1. ภาพรวม

ระบบนี้ให้หมอพื้นบ้านที่ได้รับการรับรองบันทึกทะเบียนการรักษา ม.บ.5 บนมือถือ ส่งข้อมูลเข้า HOSxP ของหน่วยบริการในพื้นที่ และส่งต่อผู้ป่วยกับโรงพยาบาลได้ทั้งสองทาง

**ปัญหาที่แก้**

- หมอพื้นบ้านต้องจดทะเบียนการรักษา (ม.บ.5) และเก็บไว้ไม่น้อยกว่า 5 ปี ตามระเบียบ สธ. ว่าด้วยการรับรองหมอพื้นบ้าน พ.ศ. 2562 แต่ปัจจุบันเป็นกระดาษ ข้อมูลจึงไม่ถึงแพทย์และใช้เป็นหลักฐานไม่ได้
- ยังไม่มีระบบส่งต่อหรือร่วมรักษาระหว่างหมอพื้นบ้านกับโรงพยาบาล ผู้ป่วยเลือกไปเองโดยที่สองฝ่ายไม่รู้ข้อมูลกัน
- ผลข้างเคียงจากการรักษาพื้นบ้านไม่ถูกติดตาม ทั้งที่เป็นข้อกังวลหลักของแพทย์แผนปัจจุบัน

**เป้าหมาย**

1. หมอพื้นบ้านบันทึกการรักษา 1 ครั้งได้ภายใน 2 นาที ด้วยเสียงหรือการแตะ
2. แพทย์ใน HOSxP เห็นประวัติการรักษาพื้นบ้านของผู้ป่วยใน EMR
3. ส่งต่อผู้ป่วยได้ทั้งจากโรงพยาบาลไปหมอ และจากหมอไปโรงพยาบาล พร้อมติดตามสถานะได้
4. ข้อมูลรวมระดับพื้นที่ใช้เป็นหลักฐานเชิงประจักษ์และรายงานต่อ สสจ. ได้

**ขอบเขต**

| อยู่ในขอบเขต | อยู่นอกขอบเขต (ระยะนี้) |
| --- | --- |
| ทะเบียนการรักษา ม.บ.5 ดิจิทัล | ระบบยื่นขอรับรอง ม.บ.1–ม.บ.6 ออนไลน์ (มีระบบ ttm.dtam อยู่แล้ว) |
| ทะเบียนหมอพื้นบ้านในพื้นที่ (อ่านจากข้อมูลรับรอง) | การแปลงตำราโบราณเป็นดิจิทัล |
| ส่งต่อผู้ป่วยสองทาง | การเบิกจ่ายหรือเรียกเก็บค่าบริการ |
| แสดงข้อมูลใน HOSxP และแดชบอร์ด รพ.สต./สสจ. | คลังความรู้และตำรับยาแบบเปิดเผย |
| รายงานอาการไม่พึงประสงค์ | |

**สมมติฐาน (ต้องยืนยันก่อนเริ่มพัฒนา)**

- หน่วยบริการนำร่องใช้ HOSxP และยอมให้เชื่อมผ่าน API กลาง
- ข้อมูลรายชื่อหมอที่ได้รับการรับรองขอได้จาก สสจ. หรือระบบ ttm.dtam.moph.go.th
- หมอพื้นบ้านหรือผู้ช่วย (ลูกหลาน, อสม.) มีสมาร์ตโฟน

## 2. ผู้ใช้และบทบาท

ระบบมีผู้ใช้ 5 บทบาท หมอพื้นบ้านเป็นผู้ใช้หลัก จึงออกแบบทุกอย่างเพื่อผู้สูงอายุก่อน

| บทบาท | ลักษณะ | สิ่งที่ทำในระบบ | ช่องทาง |
| --- | --- | --- | --- |
| หมอพื้นบ้าน | อายุ 47–89 ปี, ส่วนใหญ่จบ ป.4, พูดภาษาถิ่น, มีเลขหนังสือรับรอง ม.บ.3 | บันทึกการรักษา, รับเคสส่งต่อ, ส่งต่อผู้ป่วยไป รพ. | แอปมือถือ (หรือ LINE LIFF) |
| ผู้ช่วยบันทึก | ลูกหลาน, ศิษย์ หรือ อสม. ที่หมอมอบหมาย | บันทึกแทนหมอ โดยหมอเป็นผู้ยืนยัน | แอปมือถือ |
| แพทย์ / แพทย์แผนไทย รพ. | ใช้ HOSxP Doctor Workbench | ดูประวัติพื้นบ้านใน EMR, ส่งต่อหาหมอ, รับเคสจากหมอ | เว็บพอร์ทัล + ปุ่มลิงก์จาก HOSxP |
| จนท. รพ.สต. / สสจ. | กลุ่มงานแพทย์แผนไทยฯ ของ สสจ. | นำเข้ารายชื่อหมอ, ดูแดชบอร์ด, ติดตามอาการไม่พึงประสงค์ | เว็บพอร์ทัล |
| ผู้ป่วย | ประชาชนที่รักษากับหมอพื้นบ้าน | ให้ความยินยอม, ตรวจสอบหมอด้วย QR, รายงานอาการหลังรักษา | LINE OA (ไม่ต้องติดตั้งแอป) |

**สิทธิ์การเข้าถึงข้อมูล**

- หมอเห็นเฉพาะผู้ป่วยที่ตนเองรักษา หรือที่ถูกส่งต่อมาหาตนเอง
- แพทย์เห็นบันทึกพื้นบ้านได้เมื่อผู้ป่วยให้ความยินยอมแบบเปิดเผยกับหน่วยบริการไว้
- สสจ. เห็นข้อมูลรวมที่ไม่ระบุตัวบุคคล ยกเว้นเคสอาการไม่พึงประสงค์ที่ต้องติดตาม
- ตำรับยาและคาถาเป็นความลับของหมอ บันทึกแค่ชื่อสมุนไพรหลักและรูปแบบยา ไม่บังคับเปิดสูตร (สอดคล้องมาตรา 15 พ.ร.บ.คุ้มครองฯ 2542)

## 3. User flows หลัก

มี 5 flow หลัก flow A กับ C คือหัวใจของเดโม

**A. หมอบันทึกการรักษา (ม.บ.5)**

1. หมอเปิดแอป แตะ "รักษาคนไข้"
2. ค้นหาผู้ป่วย: สแกนบัตรประชาชน (OCR/QR) หรือพิมพ์เลข 13 หลัก ถ้าไม่เคยมา ระบบสร้างผู้ป่วยใหม่
3. ครั้งแรก: ขอความยินยอม (อ่านให้ฟังเป็นเสียง + เซ็นชื่อบนจอ) พร้อมบันทึกโรคประจำตัว ประวัติแพ้ น้ำหนัก ส่วนสูง
4. กดปุ่มไมค์เล่าอาการและการรักษาเป็นภาษาถิ่น ระบบถอดเสียงและเติมช่อง ม.บ.5 ให้อัตโนมัติ: อาการ ตรวจร่างกาย วินิจฉัย การรักษา
5. หมอแตะเลือกกรรมวิธีจากรายการที่ตนได้รับรับรองเท่านั้น (เช่น นวดเส้น, ประคบ, ยาต้ม) ตามข้อ 28 ของระเบียบ
6. ตรวจทาน แก้ไข แล้วกด "บันทึก" ระบบตั้งนัดติดตามอาการตามที่หมอกำหนด
7. ถ้าพบสัญญาณอันตราย (red flag) ระบบเตือนและเสนอให้ส่งต่อ (ไป flow D)

**B. แพทย์ดูประวัติพื้นบ้านใน HOSxP**

1. ผู้ป่วยมาโรงพยาบาล เปิด visit ตามปกติ
2. Doctor Workbench แสดงแถบเตือน "มีประวัติรักษากับหมอพื้นบ้าน 2 ครั้งใน 30 วัน"
3. แพทย์กดดู timeline: วันที่ ชื่อหมอ ประเภท กรรมวิธี สมุนไพรหลัก ผล และอาการไม่พึงประสงค์
4. ถ้าสมุนไพรอาจตีกับยาที่กำลังสั่ง (เช่น ขี้เหล็ก + ยาที่มีผลต่อตับ) ระบบแสดงคำเตือน

**C. โรงพยาบาลส่งต่อผู้ป่วยไปหมอพื้นบ้าน**

1. แพทย์กด "ส่งต่อหมอพื้นบ้าน" จาก HOSxP หรือเว็บพอร์ทัล เช่น ผู้ป่วยอัมพฤกษ์อัมพาต หรือหญิงหลังคลอด
2. เลือกประเภทหมอและกรรมวิธีที่ต้องการ ระบบแสดงหมอที่ได้รับรับรองในกรรมวิธีนั้น เรียงตามระยะทางจากบ้านผู้ป่วย
3. แนบข้อมูลส่งต่อ: การวินิจฉัย ข้อห้าม (เช่น ห้ามนวดบริเวณแผล ห้ามใช้ความร้อน) และยาที่ใช้อยู่
4. หมอได้รับแจ้งเตือน กดรับหรือปฏิเสธเคส
5. หมอบันทึกการรักษา (flow A) ทุกครั้งที่รักษา ผลส่งกลับไปที่แพทย์ผู้ส่ง
6. หมอกด "จบการรักษา" พร้อมสรุปผล เคสปิดและแจ้งแพทย์

**D. หมอส่งต่อผู้ป่วยไปโรงพยาบาล**

1. หมอกด "ส่งต่อโรงพยาบาล" หรือระบบเสนอจาก red flag
2. เลือกความเร่งด่วน: ฉุกเฉิน (แสดงปุ่มโทร 1669 ทันที) / ไม่ฉุกเฉิน
3. ระบบส่งใบส่งต่อพร้อมบันทึก ม.บ.5 ล่าสุดไป รพ.สต. หรือโรงพยาบาลในพื้นที่ และออก QR ให้ผู้ป่วยถือไป
4. เจ้าหน้าที่สแกน QR เมื่อผู้ป่วยมาถึง สถานะเปลี่ยนเป็น "มาถึงแล้ว" และหมอได้รับแจ้ง

สถานะการส่งต่อ (ใช้ร่วมกันทั้ง C และ D): ส่งแล้ว → รับเคส / ปฏิเสธ → กำลังรักษา → จบการรักษา ส่วนเคสที่ไม่มีการตอบรับภายใน 72 ชั่วโมงจะเตือนผู้ส่ง (ค่า 72 ชั่วโมงเป็นค่าเสนอ ต้องตกลงกับพื้นที่)

**E. ค้นหาหมอและตรวจสอบหมอ (ผู้ป่วย/ประชาชน):** สแกน QR บนบัตรหมอ → เห็นชื่อ เลขหนังสือรับรอง ประเภทและกรรมวิธีที่รับรอง วันหมดอายุ และสถานะ (ใช้ได้ / พักใช้ / หมดอายุ)

## 5. Data model

ระบบมี 9 entity หลัก ชื่อฟิลด์อิงตามแบบฟอร์ม ม.บ.1-1, ม.บ.3 และ ม.บ.5 ตามประกาศกรมการแพทย์แผนไทยฯ เรื่องกำหนดแบบ พ.ศ. 2563

| Entity | ฟิลด์หลัก | ที่มา |
| --- | --- | --- |
| healer (หมอพื้นบ้าน) | healer_id, cert_no (เช่น ขก 00001), cid, prename, fname, lname, birthdate, phone, line_id, address (บ้านเลขที่…รหัสไปรษณีย์), lat/lng, proposer_type (หมู่บ้าน/อปท.), proposer_name | ม.บ.1-1, ม.บ.3 |
| certificate (หนังสือรับรอง) | cert_no, healer_id, issued_date, expire_date (+5 ปี), province_code, issuer, conditions, status (ใช้ได้/พักใช้/เพิกถอน/หมดอายุ), is_replacement, renewals[] | ม.บ.3 (หน้า-หลัง) |
| healer_competency | healer_id, healer_type (6 ประเภท), method_code (122 กรรมวิธี), nature (ลักษณะ 1/2), service_area | ม.บ.3 + ประกาศคณะกรรมการฯ 2562 |
| patient | patient_id, cid, prename, fname, lname, sex, birthdate, address, phone, chronic_disease, allergy (ยา/อาหาร), weight, height, hosxp_hn (nullable) | ม.บ.5 (ส่วนผู้ป่วย) |
| consent | patient_id, healer_id, scope (record / share_facility), method (เซ็น/เสียง), signed_at, revoked_at, evidence_file | PDPA |
| treatment (บันทึก ม.บ.5 ต่อครั้ง) | treatment_id, patient_id, healer_id, visit_no (ครั้งที่), visit_datetime, symptom, local_disease_name, physical_exam, diagnosis, treatment_text, result (หาย/ทุเลา/ไม่ดีขึ้น/แย่ลง), follow_up_date, note, audio_file, referral_id, recorded_by, confirmed_by, synced_at | ม.บ.5 (ตารางการรักษา) |

| referral | referral_id, direction (to_healer / to_facility), patient_id, from_party, to_party, urgency, reason, diagnosis, precautions, current_meds, status, qr_token, created_at, accepted_at, closed_at, outcome | ออกแบบใหม่ |
| adverse_event | event_id, treatment_id, reporter, onset_date, description, severity, action_taken, reviewed_by | ออกแบบใหม่ |

**Master data**

- method_master: 122 กรรมวิธี แบ่ง 6 ด้าน (นวด 30, สมุนไพร 43, พิธีกรรม 27, กระดูก 6, วินิจฉัย 7, อื่นๆ 9) ต้องกำหนดรหัสเองเพราะประกาศไม่มีรหัส
- herb_master: ชื่อมาตรฐาน + ชื่อวิทยาศาสตร์ + ชื่อท้องถิ่นหลายชื่อ + คำเตือนที่ผ่านการตรวจทาน
- red_flag_rule: กฎสัญญาณอันตราย ต่อประเภทหมอ ต้องผ่านการรับรองจากแพทย์ก่อนใช้

**Mapping ไป HOSxP** (ต้องตรวจกับฐานข้อมูลจริง เพราะคลังความรู้ HOSxP ไม่มีรายละเอียดฟิลด์ของตารางเหล่านี้)

| ฝั่งเรา | HOSxP | หมายเหตุ |
| --- | --- | --- |
| patient.cid → hosxp_hn | patient.cid → patient.hn | จับคู่ด้วย CID |
| healer | ทะเบียนผู้ให้บริการด้านแพทย์แผนไทย (HOSxPHealthMedManager) | ใช้ cert_no แทนเลขใบประกอบวิชาชีพ |
| method_master | health_med_operation_item | เพิ่มรายการกลุ่ม "หมอพื้นบ้าน" ส่วน ICD10-TM อาจไม่มีรหัสตรง |
| treatment + treatment_item | health_med_service* (ผูก VN) | บันทึกนอกหน่วยบริการไม่มี VN จึงต้องตัดสินใจว่าจะสร้าง visit หรือเก็บในตารางเสริม (ดูหัวข้อ 6) |
| referral | ระบบ Refer ของ HOSxP (referin / referout) | ส่งต่อไปหน่วยบริการแล้วจะเป็น referin อย่างไร ต้องตรวจสอบ |

## 6. Integration

เริ่มจากการเชื่อมแบบอ่านอย่างเดียวกับ HOSxP ผ่าน adapter ที่ติดตั้งในหน่วยบริการ จะเขียนกลับเข้าฐานข้อมูล HOSxP ก็ต่อเมื่อผ่านการตรวจโครงสร้างตารางและได้รับอนุญาตจากหน่วยบริการแล้ว

**6.1 HOSxP Adapter (ติดตั้งใน รพ./รพ.สต.)**

- เป็น service เล็กๆ ที่ต่อฐานข้อมูล HOSxP (MySQL/MariaDB) ด้วย user สิทธิ์อ่านอย่างเดียว แล้วเชื่อมออกไปที่ Cloud API (outbound HTTPS) ไม่ต้องเปิด port เข้ามาในโรงพยาบาล
- GET /patients/{cid} → คืน hn และข้อมูลพื้นฐาน (จาก patient) พร้อมประวัติแพ้ (opd_allergy) เมื่อผู้ป่วยยินยอม
- GET /patients/{hn}/medications → ยาที่ได้รับใน 90 วัน (จาก opitemrece + drugitems) สำหรับใบส่งต่อและการเตือนยาตีกัน
- ปุ่มใน HOSxP: ใช้เมนู Task/ลิงก์ภายนอกที่ HOSxP รองรับ เปิดเว็บพอร์ทัลพร้อม HN (ต้องตรวจสอบว่าเวอร์ชันที่ใช้ทำได้อย่างไร)
- เฟสถัดไป (Later): เขียนบันทึกการรักษาเข้า health_med_service* และสร้าง referin เมื่อผู้ป่วยที่หมอส่งต่อมาถึง

**6.2 การจับคู่ผู้ป่วย**

1. ใช้ CID เป็นกุญแจหลัก (ตรวจ checksum ก่อนส่ง)
2. ถ้าไม่มี CID (เช่น ผู้ไม่มีสถานะทางทะเบียน) ใช้ ชื่อ + สกุล + วันเกิด แล้วให้เจ้าหน้าที่ยืนยันการจับคู่เอง ไม่จับคู่อัตโนมัติ
3. ผู้ป่วยที่ไม่เคยมี HN เก็บไว้ฝั่งเราอย่างเดียว จะจับคู่เมื่อมาโรงพยาบาลครั้งแรก

**6.3 ระบบภายนอกอื่นๆ**

| ระบบ | ใช้ทำอะไร | สถานะ |
| --- | --- | --- |
| ttm.dtam.moph.go.th ระบบภูมิปัญญาการแพทย์แผนไทยและสมุนไพร | ตรวจสอบเลขหนังสือรับรองและสถานะหมอ | ไม่ทราบว่ามี API; MVP ใช้ไฟล์นำเข้าจาก สสจ. |
| LINE Messaging API + LIFF | แจ้งเตือนหมอและผู้ป่วย, หน้าตรวจสอบหมอ | มี API สาธารณะ |
| บริการถอดเสียงภาษาไทย | FR-21 บันทึกด้วยเสียง | ต้องทดสอบความแม่นกับภาษาอีสาน เหนือ ใต้ |
| Claude API | แยกข้อความที่ถอดเสียงเป็นช่อง ม.บ.5 และจับคู่ชื่อสมุนไพร | ส่งเฉพาะข้อความที่ตัดข้อมูลระบุตัวตนออกแล้ว |
| 1669 (สพฉ.) | ปุ่มโทรฉุกเฉิน | ลิงก์ tel: ไม่ต้องเชื่อมระบบ |

**6.4 มาตรฐานข้อมูล:** API ภายนอกออกแบบให้ใกล้เคียง FHIR R4 (Patient, Practitioner, Encounter, Procedure, ServiceRequest, AdverseEvent) เพื่อต่อยอดกับระบบอื่นได้ภายหลัง

## 7. Non-functional requirements

ข้อมูลในระบบเป็นข้อมูลสุขภาพซึ่งเป็นข้อมูลอ่อนไหวตาม PDPA มาตรา 26 จึงต้องมีความยินยอมชัดแจ้งทุกครั้ง

| หมวด | Requirement |
| --- | --- |
| PDPA และความยินยอม | เก็บหลักฐานความยินยอม (ลายเซ็นหรือเสียง) แยกขอบเขต "บันทึก" กับ "เปิดเผยกับหน่วยบริการ" ถอนได้ตลอด และมี audit log ทุกการเปิดดู |
| ความลับของภูมิปัญญา | ไม่บังคับบันทึกสูตรยา ปริมาณ หรือคาถา; ไฟล์เสียงต้นฉบับเห็นเฉพาะหมอเจ้าของ |
| ความปลอดภัย | TLS 1.2+, เข้ารหัสข้อมูลที่เก็บ (AES-256) ทั้งบน server และบนมือถือ, เก็บ CID แบบเข้ารหัสและค้นด้วย hash, กำหนดสิทธิ์ตามบทบาท (RBAC) |
| ที่ตั้งข้อมูล | เก็บบน cloud ในประเทศไทย (เช่น MOPH Cloud หรือผู้ให้บริการที่มี region ไทย) |
| การเก็บรักษา | เก็บบันทึก ม.บ.5 ไม่น้อยกว่า 5 ปีตามระเบียบ แก้ไขได้แต่เก็บประวัติทุกเวอร์ชัน ไม่ลบจริง |
| ออฟไลน์ | บันทึกได้แม้ไม่มีสัญญาณ เก็บคิวไว้บนเครื่อง sync อัตโนมัติ; ถอดเสียงทำตอน sync ได้ |
| ผู้ใช้สูงอายุ | ตัวอักษรไม่ต่ำกว่า 20 pt, ปุ่มใหญ่ไม่ต่ำกว่า 56 px, หน้าละไม่เกิน 1 งาน, มีเสียงอ่านนำทุกหน้า, ใช้ไอคอนคู่กับคำ, ไม่ต้องจำรหัสผ่าน |
| ภาษา | UI ภาษาไทย; รับเสียงภาษาอีสาน เหนือ ใต้; เก็บชื่อโรคและสมุนไพรตามคำที่หมอใช้ คู่กับคำมาตรฐาน |
| อุปกรณ์ | Android 9+ และ iOS 15+, ทำงานได้บนมือถือ RAM 2 GB, ขนาดแอปไม่เกิน 50 MB |
| ประสิทธิภาพ | เปิดหน้าประวัติพื้นบ้านจาก HOSxP ภายใน 3 วินาที; แจ้งเตือนส่งต่อถึงปลายทางภายใน 1 นาที |
| ความพร้อมใช้งาน | Cloud API uptime ไม่ต่ำกว่า 99.5% (ระยะนำร่อง); แอปใช้งานต่อได้แบบออฟไลน์เมื่อ server ล่ม |
| ขอบเขตทางคลินิก | ระบบไม่แนะนำการรักษา ไม่ประเมินประสิทธิผลของหมอ; red flag ทำได้เพียงเตือนและเสนอส่งต่อ |

## 8. Architecture และ tech stack

ทุกแอปคุยกับ Cloud API ตัวเดียว ส่วน HOSxP Adapter ในโรงพยาบาลเป็นฝ่ายเริ่มการเชื่อมต่อออกมาเสมอ จึงไม่ต้องเปิด port เข้าเครือข่ายโรงพยาบาล

**แผนภาพ: ทุกข้อมูลผ่าน Cloud API ส่วน HOSxP เชื่อมออกทางเดียวแบบอ่านอย่างเดียว**

## 9. แผน MVP สำหรับ Hackathon

MVP ต้องเดโม flow A → B → C ได้ครบใน 5 นาที โดยใช้ฐานข้อมูล HOSxP จำลองที่มีข้อมูลทดสอบ ไม่ใช้ข้อมูลผู้ป่วยจริง

**ลำดับการสร้าง** (ทำตามลำดับ ถ้าเวลาไม่พอให้ตัดจากท้าย)

1. Master data: หมอตัวอย่าง 5 คน (ครบ 6 ประเภทไม่จำเป็น), กรรมวิธีที่ใช้ในเดโม ประมาณ 20 รายการ, สมุนไพร 30 รายการพร้อมชื่อท้องถิ่น
2. ฐานข้อมูล HOSxP จำลอง: ตาราง patient, opd_allergy, opitemrece ที่มีผู้ป่วยสมมติ 3 คน
3. แอปหมอ: เข้าระบบ, ค้นผู้ป่วย, ความยินยอม, ฟอร์ม ม.บ.5 (FR-01, 02, 10, 11, 20, 22)
4. บันทึกด้วยเสียง + แยกช่องด้วย LLM (FR-21, 23) เป็นจุดเด่นของเดโม
5. เว็บพอร์ทัลแพทย์: timeline พื้นบ้านที่เปิดด้วย HN (FR-50)
6. ส่งต่อสองทาง + แจ้งเตือน LINE (FR-40, 41, 42)
7. Red flag (FR-30) กฎ 3–5 ข้อ
8. แดชบอร์ดหน้าเดียว (FR-60)
9. ออฟไลน์ (FR-25) — ถ้าเวลาไม่พอ ให้เดโมด้วยการปิด Wi-Fi แล้ว sync ให้ดูแทน

## 10. ความเสี่ยง คำถามที่เปิดอยู่ และแหล่งอ้างอิง

ความเสี่ยงสูงสุดคือหมอพื้นบ้านไม่ใช้งาน ไม่ใช่เทคโนโลยี

| ความเสี่ยง | ผลกระทบ | แนวทางรับมือ |
| --- | --- | --- |
| หมอสูงอายุไม่สะดวกใช้มือถือ | ไม่มีข้อมูลเข้าระบบ | บันทึกด้วยเสียง + ผู้ช่วยบันทึก (ลูกหลาน, อสม.) + ทดสอบกับหมอจริงก่อนออกแบบเสร็จ |
| หมอกังวลว่าจะถูกตรวจสอบหรือถูกเอาความรู้ไป | ไม่ยอมบันทึกหรือบันทึกไม่ครบ | ไม่บังคับสูตรยา, หมอเป็นเจ้าของข้อมูล, ออกแบบร่วมกับเครือข่ายหมอพื้นบ้าน |
| โรงพยาบาลไม่อนุญาตให้เชื่อมฐานข้อมูล HOSxP | ไม่มี flow B | เริ่มจาก read-only adapter; ทางสำรองคือเว็บพอร์ทัลแยกที่ค้นด้วย CID |
| แพทย์ไม่กล้าส่งต่อเพราะกังวลความรับผิดชอบ | ไม่มี flow C | เริ่มจากกลุ่มเสี่ยงต่ำ (อัมพฤกษ์ฟื้นฟู, หลังคลอด) และให้ สสจ. ออกแนวทางส่งต่อ |
| ถอดเสียงภาษาถิ่นไม่แม่น | บันทึกผิด | หมอต้องตรวจและยืนยันทุกครั้ง, เก็บเสียงต้นฉบับไว้ |
| กฎ red flag พลาด | ผู้ป่วยได้รับอันตราย | ระบบไม่รับประกันความปลอดภัย, กฎต้องผ่านแพทย์รับรอง, แสดงปุ่ม 1669 เสมอ |
| ซ้ำซ้อนกับระบบของกรมการแพทย์แผนไทยฯ | ไม่ได้รับการสนับสนุน | ไม่ทำระบบรับรอง อ่านข้อมูลจาก ttm.dtam แทนการสร้างทะเบียนซ้ำ |
